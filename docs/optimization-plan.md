# 项目优化方案

> 日期：2026-04-04  
> 范围：ECG Diagnosis Suite 当前主干  
> 目标：在不打断现有可用功能的前提下，提高可维护性、稳定性和后续迭代效率

## 一、当前判断

项目已经跨过“能跑”的阶段，当前的主要问题不是功能缺失，而是几个核心模块开始变重：

- 前端主控制器过大，状态、上传、持久化、同步逻辑耦合
- 后端诊断接口承担了过多职责
- 运行期日志仍以 `print` 为主，缺少正式可观测性
- 兼容层和历史接口仍保留，心智模型开始分裂
- 存在少量框架弃用警告，短期不影响运行，长期会影响升级

因此优化方向应该以“结构收敛”和“运行质量提升”为主，而不是继续扩功能。

## 二、优化目标

本轮优化的核心目标有四个：

1. 降低前后端核心模块复杂度
2. 提高排障和运行可观测性
3. 明确旧接口和兼容逻辑的淘汰路径
4. 为后续功能开发建立稳定边界

## 三、优化原则

- 不做大爆炸重写，采用分阶段重构
- 每个阶段都保持测试可运行
- 优先拆高耦合模块，不优先做表面美化
- 先解决“未来每次修改都会痛”的点

## 四、分阶段方案

## P0：结构止损

### 1. 前端状态管理拆层

目标：拆解 `frontend/src/controllers/useWorkspaceController.ts`

当前问题：

- 单文件超过 1000 行
- 同时处理 UI、会话、上传、诊断提交、云端同步、持久化
- 任一流程变更都可能影响整条链路

执行方案：

- 抽离 `session` 相关 reducer / actions
- 抽离 `composer` 与附件校验逻辑
- 抽离 `submission` 与上传状态机
- 抽离远端 chat/auth 同步逻辑为单独 service 或 hook
- 保持页面层只消费组合后的 controller 接口

验收标准：

- 主 controller 下降到 300-500 行量级
- 每个子模块职责单一
- 现有前端测试继续通过

### 2. 后端诊断链路 service 化

目标：拆解 `backend/app/api/diagnosis.py`

当前问题：

- API 层同时处理上传校验、临时文件、质量门控、模型推理、持久化、异常映射
- 图片路径与 `.dat/.hea` 路径共享逻辑不够明确

执行方案：

- 新建诊断 application service，统一组织诊断流程
- 将“文件准备”“图像诊断”“信号诊断”“结果保存”拆为独立函数或类
- API 层只保留参数校验和响应返回
- 统一异常类型，避免在路由层散落大量错误处理

验收标准：

- 路由层明显变薄
- 图片诊断与信号诊断流程可单独测试
- `backend/tests` 继续全绿

### 3. 把运行期 `print` 全量替换为 logging

目标：规范日志输出

当前问题：

- 核心接口和模型/加载服务大量使用 `print`
- 容器环境中不利于筛查问题、汇总日志、定位请求链路

执行方案：

- 在 API、service、ML 入口统一使用 `logging`
- 日志分级为 `info / warning / error`
- 为诊断请求增加基础上下文：输入类型、文件名、用户态、关键阶段耗时

验收标准：

- 核心运行路径不再依赖 `print`
- 失败日志能定位到阶段和原因

## P1：边界收敛

### 4. 收拢历史接口与兼容逻辑

目标：明确保留与淘汰边界

执行方案：

- 为 `/api/history` 标记淘汰时间或版本
- 前端全部收口到 chat/session 体系
- 文档明确“推荐接口”和“兼容接口”

验收标准：

- 新功能不再接入旧历史接口
- 文档与代码行为一致

### 5. 报告服务继续拆分

目标：重构 `backend/app/services/diagnosis_report_service.py`

执行方案：

- 分离模板报告构建器
- 分离 LLM provider 客户端
- 分离输出解析与 fallback
- 为 provider 增加统一接口，避免后续分支扩散

验收标准：

- 报告逻辑结构清晰
- 新增 provider 不需要改动主流程太多

### 6. 安全配置基线收紧

执行方案：

- 强制生产环境覆盖默认 `SECRET_KEY`
- 明确区分开发与生产数据库配置
- 检查认证相关 cookie、CORS、Origin 校验的生产默认值

验收标准：

- 生产配置不存在明显默认弱项
- 配置文档与实际行为一致

## P2：质量提升

### 7. 消化框架弃用警告

执行方案：

- 把 Pydantic 的 class-based `Config` 迁移到 `ConfigDict`
- 把 SQLAlchemy `declarative_base()` 迁移到 2.x 推荐写法

验收标准：

- `pytest -q` 不再出现当前这批弃用 warning

### 8. 补更贴近业务的回归测试

执行方案：

- 增加图片诊断成功路径测试
- 增加 `.dat + .hea` 同名/错名/缺失场景测试
- 增加 chat 会话与认证边界测试
- 增加日志与失败回退行为测试

验收标准：

- 测试重点覆盖主业务路径，而不是只覆盖工具函数

### 9. 建立性能基线

执行方案：

- 记录图片诊断和信号诊断的平均耗时
- 记录模型加载时长和首请求时延
- 对上传、转换、推理、报告生成分别计时

验收标准：

- 能明确知道慢在哪里
- 后续优化前后有可比数据

## 五、推荐执行顺序

建议按下面顺序推进：

1. 前端 controller 拆层
2. 后端诊断 service 化
3. logging 替换 `print`
4. 收拢旧接口
5. 报告服务拆分
6. 安全配置基线
7. 消化 warning
8. 补回归测试
9. 建性能基线

## 六、排期建议

如果按一个人持续推进，比较现实的节奏是：

- 第 1 周：前端 controller 拆层
- 第 2 周：后端诊断 service 化 + logging
- 第 3 周：历史接口收拢 + 报告服务拆分
- 第 4 周：warning 清理 + 测试补强 + 性能基线

## 七、本轮优化完成标志

满足以下条件，可视为本轮优化完成：

- 前后端核心大文件明显瘦身
- 核心运行路径日志正规化
- 旧接口不再是默认路径
- `pytest -q` 通过且 warning 显著减少
- 文档、配置、代码行为三者一致

## 八、结论

当前项目最优的优化路线，不是继续加新页面或新模型，而是优先做“结构减压”。  
只要先把前端 controller、后端诊断链路和运行日志这三件事做好，后面的功能开发成本会明显下降，系统也会更接近真正可持续维护的工程项目。
