# Auth & Chat History Cloud Storage Design

Date: 2026-04-02

## Summary

Add user registration/login (email + password) and cloud-based conversation history storage to the ECG Diagnosis Suite. The app transitions from a purely local tool to a public SaaS platform where anonymous users can try the diagnosis feature, then optionally sign up to persist their history across devices.

## Requirements

- Email + password registration and login (no email verification for now)
- JWT-based authentication with HttpOnly cookie for refresh token
- Complete conversation history stored in backend database
- Anonymous users can use diagnosis without logging in
- One-time migration of local history to cloud on first login
- Cross-device access to conversation history for logged-in users

**`refresh_tokens`**

| Column | Type | Constraints | Description |
|---|---|---|---|
| id | Integer | PK, auto-increment | Token record ID |
| user_id | Integer | FK -> users.id ON DELETE CASCADE, not null | Owner |
| token_hash | String(255) | unique, not null | SHA-256 hash of the refresh token |
| family_id | String(255) | not null, indexed | Token family for replay detection |
| replaced_by_id | Integer | FK -> refresh_tokens.id, nullable | New token that replaced this one |
| revoked_at | DateTime(tz) | nullable | When this token was revoked |
| expires_at | DateTime(tz) | not null | Expiry time |
| created_at | DateTime(tz) | server default utcnow() | Creation time |

Indexes: `ix_refresh_tokens_user` on `(user_id)`, `ix_refresh_tokens_expires` on `(expires_at)`

**Refresh token lifecycle:**
- On login/register: create new token row with a fresh `family_id`, `replaced_by_id = null`, `revoked_at = null`
- On refresh: find token by hash, verify not expired and not revoked. Create new token row with same `family_id`, set old row's `replaced_by_id` to new row's id and `revoked_at = now()`
- On replay detection: if a request uses a token that has `revoked_at` set (meaning it was already replaced), revoke the entire `family_id` (set `revoked_at` on all tokens in that family). This detects token theft.
- On logout: revoke the current token (set `revoked_at = now()`), clear cookie
- Periodic cleanup: delete rows where `expires_at < now()` and `revoked_at` is set (already expired and revoked)

### Existing Table Change

`diagnosis_records`: add nullable `user_id` column (FK -> users.id ON DELETE SET NULL).

Index: `ix_diagnosis_records_user` on `(user_id, created_at DESC)`

**Data separation policy:**
- `diagnosis_records` is an internal analytics/audit log. It is NOT exposed to users via any API.
- The existing `GET /api/history` endpoint will be removed/deprecated in this release.
- Deleting a chat session does NOT affect `diagnosis_records` (they are independent data with no FK link to sessions).
- Account deletion (hard-delete user row): `diagnosis_records.user_id` is set to NULL via `ON DELETE SET NULL` FK. The record itself is retained for aggregate analytics, de-identified.

### Migration Strategy

- Add Alembic to the project. Initial migration captures existing `diagnosis_records` table + all new tables.
- Production deployments must run `alembic upgrade head` before starting the app.
- Keep `Base.metadata.create_all()` only for dev/test bootstrap (when no migrations table exists).
- Document migration commands in CLAUDE.md.

## Backend API

### Auth Router (`/api/auth`)

| Endpoint | Method | Auth | Description |
|---|---|---|---|
| `/api/auth/register` | POST | None | Register with email + password (min 8 chars) + optional display_name. Sets refresh cookie. Returns access token + user info. |
| `/api/auth/login` | POST | None | Login with email + password. Sets refresh cookie. Returns access token + user info. |
| `/api/auth/refresh` | POST | Cookie | Reads refresh token from `rt` cookie. Issues new access token + rotates refresh cookie. Also returns user info (id, email, display_name) so frontend can hydrate auth state without an extra `/me` call. |
| `/api/auth/logout` | POST | Cookie | Revokes refresh token, clears cookie. |
| `/api/auth/me` | GET | Bearer | Returns current user profile. |
| `/api/auth/change-password` | POST | Bearer | Body: `{ old_password, new_password }`. Revokes all refresh tokens for this user. Other devices will need to re-login when their current access tokens expire (within 15 min). Clears refresh cookie. |
| `/api/auth/delete-account` | POST | Bearer | Hard-deletes the user row. CASCADE deletes chat_sessions, chat_messages, refresh_tokens. diagnosis_records.user_id set to NULL via SET NULL FK. Clears `rt` cookie in response. |

**Account enumeration prevention:** Login and register return the same generic error message ("Invalid credentials" or "Registration failed") whether the email exists or not.

**Token spec:**
- Access token: 15 min expiry, HS256, payload: `{ sub: user_id, exp }`. Returned in response body. Stored in JS memory only (never localStorage).
- Refresh token: 7 day expiry, opaque random string. Stored in `rt` HttpOnly cookie.
- Signing key: `SECRET_KEY` from config (must be set via env var in production, fail to start if it's the default value).
- Cookie attributes: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/api/auth`. Cookie name: `rt` (no `__Host-` prefix because `Path=/api/auth` is narrower than `/`). In development (`DEBUG=True`), `Secure` is relaxed to allow localhost.

**CSRF protection:**
- SameSite=Lax covers most cases. Validate `Origin` header on ALL auth endpoints that set or read cookies: `/api/auth/login`, `/api/auth/register`, `/api/auth/refresh`, `/api/auth/logout`. Reject requests whose `Origin` does not match configured CORS origins.

### Chat Router (`/api/chat`)

All endpoints require Bearer token auth. All endpoints scope queries by `current_user.id` from JWT. Return 404 (not 403) when session not found or not owned, to avoid enumeration.

| Endpoint | Method | Description |
|---|---|---|
| `/api/chat/sessions` | GET | List current user's sessions (id, title, updated_at). Ordered by updated_at DESC. Supports `?limit=N` (default 50). |
| `/api/chat/sessions` | POST | Create new session. Body: `{ id, title }`. Frontend provides the ID. |
| `/api/chat/sessions/{id}` | GET | Get session metadata. Does NOT return messages. |
| `/api/chat/sessions/{id}` | PATCH | Update session title. Body: `{ title }`. |
| `/api/chat/sessions/{id}` | DELETE | Delete single session and all its messages (CASCADE). |
| `/api/chat/sessions` | DELETE | Delete all sessions and their messages for the current user (for "Clear all history"). |
| `/api/chat/sessions/{id}/messages` | GET | List messages for session. Cursor-based pagination: `?cursor={created_at_iso}_{id}&limit=50`. Returns messages ordered by `(created_at, id)`. |
| `/api/chat/sessions/{id}/messages` | POST | Append messages atomically. Body: `{ messages: [...] }`. Accepts an array to ensure user message + assistant result are stored in one transaction. Server validates all message IDs are valid UUID v4. Idempotent: if any message ID already exists in the session, the entire batch is treated as a success (no duplicate insert). Updates parent session's `updated_at`. |

### Auth Middleware

- `get_current_user` dependency: parses JWT from `Authorization: Bearer <token>`, validates signature and expiry, returns User ORM object or raises 401.
- `get_optional_user` dependency: same parsing but returns `None` instead of raising on missing/invalid token. Used for diagnosis endpoints that work for both anonymous and authenticated users.
- All chat endpoints use `Depends(get_current_user)`.
- Diagnosis endpoints (`/api/diagnose`, `/api/diagnose-dat`) use `Depends(get_optional_user)`. If a user is identified, set `diagnosis_record.user_id`.

### Diagnosis Integration

The diagnosis endpoint ONLY returns the diagnosis result. It does NOT write to chat_messages.

The frontend is solely responsible for persisting conversation history:
1. User submits diagnosis -> frontend appends user message locally
2. Diagnosis completes -> frontend receives result
3. Frontend calls `POST /api/chat/sessions/{id}/messages` with both user message and assistant message atomically

This single-write-path design eliminates duplication and gives the frontend full control over session state.

### Rate Limiting

- Auth endpoints (`/register`, `/login`): 10 requests per IP per minute + 5 requests per email per minute
- `/refresh`: 10 requests per IP per minute + 20 requests per user per minute (user identified after token lookup)
- Chat write endpoints (`POST /sessions`, `POST /sessions/{id}/messages`): 30 requests per user per minute
- Use an in-memory sliding window (e.g., `slowapi` library). For multi-instance deployments, switch to Redis-backed.

## Frontend Architecture

### Auth Store (Independent Module)

Create `src/auth/store.ts` as a standalone auth store, independent of React component lifecycle:

```typescript
// Lightweight observable store, no React dependency
interface AuthState {
  user: User | null;
  accessToken: string | null;
  isLoading: boolean;
}
// Expose: getState(), subscribe(listener), setState(partial)
// Export a getToken() function for the axios interceptor
```

- Access token stored in JS memory only (the store's closure). Never persisted to localStorage.
- On app startup: attempt refresh via `/api/auth/refresh` (cookie is sent automatically). Response includes user info + access token, so one call hydrates the full auth state. If failed, store remains unauthenticated.
- `AuthProvider` React context binds to this store, re-renders on state changes.
- `apiClient` interceptor calls `store.getToken()` synchronously — no mount-order issues.

### API Client Changes (`src/api/client.ts`)

Request interceptor:
- If `store.getToken()` returns a token, attach `Authorization: Bearer <token>`.
- For auth endpoints (`/api/auth/*`), set `withCredentials: true` so cookies are sent cross-origin.

Response interceptor:
- On 401: if the request was to an auth endpoint (`/api/auth/*`), do NOT retry. Clear auth state.
- Otherwise: acquire a refresh lock (promise-based). If no refresh is in progress, call `/api/auth/refresh` (cookie sent automatically). Store the new access token. Retry the original request once with the new token. If refresh fails, clear auth state and show AuthModal.
- Mark retried requests to prevent infinite loops.

### Frontend Session ID Change

Replace current `Date.now() + '-' + Math.random().toString(36).slice(2)` with `crypto.randomUUID()`:
- Available in all modern browsers and secure contexts
- No timing leakage, stronger collision resistance
- Server validates format (UUID v4 pattern) on session creation

### New Components

1. **AuthModal** — modal with login/register tabs
   - Login: email + password fields
   - Register: email + password (min 8 chars) + confirm password + optional display_name
   - Triggered by user icon button in top bar
   - On success: close modal, hydrate auth store

2. **UserMenu** — dropdown after login
   - Display name / email
   - Change password (inline form or modal)
   - Delete account (with confirmation)
   - Logout

### Persistence Strategy

**Anonymous users (unchanged):**
- All data in localStorage (`ecg-persisted`)
- No backend interaction for session storage
- Existing "Save history on this device" toggle continues to work

**Logged-in users:**
- No localStorage cache for conversation data (V1). Source of truth is always the backend.
- On app load: fetch session list from `GET /api/chat/sessions`
- On session select: fetch messages from `GET /api/chat/sessions/{id}/messages`
- After diagnosis: call `POST /api/chat/sessions/{id}/messages` with both messages
- On session create/rename/delete: call corresponding chat API
- State is held in React state (memory) during the session

**Login migration:**
- On first login, detect local unsynced sessions in localStorage
- Prompt: "Found N local conversations. Sync to cloud?"
- If confirmed: for each session, call `POST /api/chat/sessions` then `POST /api/chat/sessions/{id}/messages` with all messages
- After successful upload: clear localStorage sessions, switch to cloud mode
- If declined: local sessions are discarded (not kept alongside cloud sessions). New sessions go to cloud only. User is informed: "Local conversations will not be saved."

**Logout:**
- Call `POST /api/auth/logout` to revoke refresh token and clear cookie
- Clear auth store (access token from memory)
- Cloud data preserved on server
- Return to anonymous mode (localStorage-based)
- Re-login restores access to all cloud history

**Sidebar UX updates:**
- "Save history on this device" toggle: hidden when logged in (redundant, cloud is the storage)
- "Clear all history" button: when logged in, shows confirmation "This will delete all conversations from the server. This cannot be undone." When anonymous, keeps current behavior.

## Security

- Password hashing: bcrypt via passlib, cost factor 12
- Password policy: minimum 8 characters
- JWT signing key from `SECRET_KEY` env var. App fails to start if it's the default placeholder value.
- Refresh tokens: HttpOnly cookie with rotation, replay detection via token families, automatic cleanup of expired tokens
- Rate limiting: per IP and per email on auth endpoints, per user on chat writes
- Account enumeration prevention: identical error messages for login/register
- CORS: in production, explicitly list allowed origins (no wildcard). In development, allow `localhost:5173`.
- CSRF: SameSite=Lax + Origin header validation on cookie-authenticated endpoints
- No user-linked medical data retained after account deletion (diagnosis_records de-identified via SET NULL)

## Error Handling

- Access token expired -> interceptor auto-refreshes via cookie -> transparent to user
- Refresh token expired or revoked -> clear auth state, show AuthModal with "Session expired" message
- Network error on chat write -> show error toast, user can retry. Data is in React state (memory) until successfully persisted.
- Network error on auth -> show error message in AuthModal
- Concurrent 401s -> single-flight refresh lock, all pending requests await same refresh promise
- Upload conflict during migration (session ID already exists on server) -> skip that session, continue with remaining
