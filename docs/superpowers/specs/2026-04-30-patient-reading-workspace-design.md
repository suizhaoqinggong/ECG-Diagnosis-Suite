# 患者阅读工作台前端重构设计文档

## 1. 背景

ECG Diagnosis Suite 当前前端以单页对话工作台为核心，重点是上传资料后在消息流中查看分析结果。这个结构对开发和诊断流程演示是成立的，但对患者场景不够友好：

- 用户首先看到的是“聊天”而不是“报告解释”。
- 历史记录是会话列表，不符合患者对“我的报告”的心理模型。
- 结果页虽然已经有摘要、发现和建议，但信息组织仍然偏工程输出，而不是患者阅读顺序。
- 登录/注册、历史保存、移动端导航仍然像工具型界面，不像完整患者产品。

本次重构目标不是给当前聊天界面换一层皮，而是把产品重构为面向患者的“阅读工作台”。

## 2. 已确认的产品定位

### 2.1 目标用户

- 主要用户是患者，而不是医生、技师或运营人员。

### 2.2 核心场景

- 场景一：患者上传 ECG、体检资料或图片，获得解释与风险提示。
- 场景二：患者拿到已有医院报告后，使用系统读懂报告并获得下一步建议。

### 2.3 主入口优先级

- 首屏主入口：`读懂已有报告`
- 首屏次入口：`上传 ECG / 健康资料`

### 2.4 内容语气

- 采用“医疗解释型”表达。
- 保留关键医学术语，但每一项都要提供简明、患者可理解的解释。
- 不走纯口语化，也不走只面向临床专业用户的术语堆叠。

### 2.5 结果页首要任务

- 用户打开结果页前 15 秒，最优先获得的是：`核心结论`
- 风险判断和下一步建议必须出现，但放在核心结论之后。

### 2.6 方案方向

- 产品方向：`B. Guided Interpreter`
- 历史记录升级为 `My Reports`
- 不继续保留“聊天会话列表”作为用户主视图

## 3. 重构目标

### 3.1 产品目标

1. 让患者把产品理解为“报告阅读与解释工具”，而不是聊天机器人。
2. 让患者在单个结果页内同时获得：
   - 核心结论
   - 风险判断
   - 下一步建议
3. 让登录和保存行为围绕“保存报告”而不是“进入账号系统”展开。
4. 让历史记录成为可检索、可回看的报告中心。
5. 在移动端和桌面端都建立稳定清晰的导航模型。

### 3.2 体验目标

1. 首屏 CTA 语义明确，避免“从哪里开始”的犹豫。
2. 结果页信息优先级稳定，不因为模型输出结构不同而出现阅读顺序混乱。
3. 风险提示必须使用文本、结构和图标，不依赖颜色单独表达。
4. 所有核心交互都满足患者端可读性和基础无障碍要求。

## 4. 非目标

- 本次不把产品扩展为长期健康管理平台。
- 本次不引入趋势图、长期复查计划中心、提醒系统等 C 端健康运营能力。
- 本次不重写后端诊断逻辑或数据模型协议。
- 本次不新增面向医生的多病例审阅控制台。

## 5. 现状与设计约束

### 5.1 当前前端结构

- 根页面基本由 `HomePage` 组合侧边栏、消息流、输入区和认证弹窗。
- 主要状态由 `useWorkspaceController` 和 `workspaceReducer` 驱动。
- 结果内容目前主要通过 `ConversationMessage` 内嵌 `HealthReport` 和 `DiagnosisReport` 呈现。
- 当前视觉语言是暖色纸张感、文档型排版、聊天工作台结构。

### 5.2 约束

- 现有会话和消息模型已经与上传、提交、结果渲染绑定，重构时应优先复用底层状态流，而不是无必要地推倒重写。
- 认证系统已存在，重构应主要调整入口语义、表单体验和账户收益表达。
- 本次设计覆盖前端信息架构、页面结构、导航、视觉系统和交互规则，不直接要求后端新增领域能力。

## 6. 总体产品结构

重构后的前端采用“患者阅读工作台”结构，核心导航如下：

- `My Reports`
- `Read a Report`
- `Upload ECG`
- `Account`

### 6.1 导航规则

- 移动端使用底部 4 项导航。
- 桌面端使用左侧报告列表或导航列，右侧为主阅读区域。
- 所有顶级目的地都需要稳定 URL 和返回路径。
- 不混用“底部导航 + 聊天抽屉 + 会话树”的多重结构。

### 6.2 页面层级

1. `Read a Report`
   - 面向首次用户和偶发用户。
   - 主 CTA 是上传已有报告、图片或文档并生成解释。
2. `Upload ECG`
   - 面向直接上传 ECG 图像、信号对和补充资料的用户。
3. `My Reports`
   - 面向已登录用户查看、检索、回看、重命名和删除历史报告。
4. `Account`
   - 面向账户信息、密码管理和数据操作。

## 7. 页面与流程设计

### 7.1 Read a Report

这是新的首屏核心入口。

#### 页面目的

- 让患者立即明白产品能做什么。
- 以最小阻力开始“读懂已有报告”的流程。
- 在首屏建立可信度和边界感。

#### 页面结构

1. Hero 区
   - 主标题强调“读懂你的检查报告”
   - 主按钮：上传已有报告
   - 次按钮：上传 ECG / 健康资料
2. 能力说明区
   - 能解释什么
   - 能帮助用户做什么
   - 不能替代医生做什么
3. 隐私与可信说明
   - 资料如何使用
   - 结果仅供参考
   - 何时需要直接就医

#### 交互原则

- 游客无需先登录即可开始一次解释流程。
- 登录收益在结果页或保存动作出现，而不是进入首页立即阻断。

### 7.2 Upload ECG

#### 页面目的

- 面向知道自己要上传 ECG 图像、波形或成对信号文件的用户。

#### 页面结构

1. 上传区
   - 支持 PDF、PNG、JPG、JPEG、`.dat + .hea`
2. 补充说明区
   - 用户填写症状、背景、报告来源
3. 上传格式提示
   - 解释支持格式和注意事项

#### 交互原则

- 拖拽上传保留，但视觉上作为文档工作流的一部分，而不是聊天区覆盖层。
- 失败时明确说明是格式问题、上传问题还是解析问题。

### 7.3 Result Page

结果页是本次重构最关键的页面。

#### 页面目标

- 在一个阅读视图内，稳定完成“结论 -> 含义 -> 风险 -> 下一步”的解释链路。

#### 固定信息优先级

1. `核心结论`
2. `这意味着什么`
3. `风险判断`
4. `下一步建议`
5. `可以问医生的问题`
6. `证据与限制`

#### 详细结构

##### 7.3.1 核心结论 Hero

- 一句话概括本次结果的主要结论。
- 展示报告类型、生成时间、来源类型。
- 文案使用医疗解释型风格，不做夸张安抚或过度技术化表达。

##### 7.3.2 这意味着什么

- 将关键医学术语逐条解释。
- 把 `summary`、`clinical_interpretation`、`key_findings` 重新组织为患者阅读段落。
- 这部分优先回答“这份报告在说什么”，而不是先展示模型概率。

##### 7.3.3 风险判断

- 必须使用明确文本标签，例如：
  - 建议立即就医
  - 建议近期复诊
  - 建议常规随访
- 不允许只用颜色表达风险。
- 风险卡片应包含简短理由说明。

##### 7.3.4 下一步建议

- 将 recommendations、follow_up、nextSteps 整理成 checklist。
- 内容应尽量转译为行动建议，例如：
  - 建议挂号科室
  - 建议复查时间
  - 哪些症状出现时需要尽快就医

##### 7.3.5 可以问医生的问题

- 基于结果自动生成少量高价值问题模板。
- 目标是帮助患者把结果页转化为就诊沟通准备材料。

##### 7.3.6 证据与限制

- 放置：
  - 模型置信度
  - 数据质量提示
  - 识别局限
  - 免责声明
- 这部分必须存在，但不能挤占首屏主要注意力。

### 7.4 My Reports

这是对当前会话列表的结构性替换。

#### 页面目的

- 让用户感觉自己在查看“保存的报告”，而不是聊天历史。

#### 列表项信息

- 报告标题
- 核心结论短摘要
- 风险等级
- 更新时间
- 来源类型

#### 支持操作

- 打开报告
- 重命名
- 删除
- 导出

#### 结构规则

- 桌面端：左侧列表，右侧详情
- 移动端：列表页进入详情页
- 支持按日期、来源、状态进行筛选或搜索

### 7.5 Account

#### 页面目的

- 将当前零散的账户动作组织成独立目的地。

#### 内容

- 当前用户信息
- 修改密码
- 删除账号
- 登录状态说明
- 与保存、隐私相关的说明

#### 交互原则

- 危险操作与普通操作明确分区。
- 删除账号流程保留确认与密码校验。

## 8. 认证与保存策略

### 8.1 游客模式

- 游客可以完成一次上传和阅读流程。
- 游客模式的价值是快速体验，不强制打断。

### 8.2 登录触发点

- 在以下时机柔和提示登录：
  - 保存报告到 `My Reports`
  - 想在其他设备查看历史
  - 想长期保留解释结果

### 8.3 认证表达

- 认证文案强调：
  - 保存报告
  - 安全访问历史记录
  - 方便再次查看
- 不强调“注册后才能继续”，除非动作本身依赖账户。

### 8.4 登录/注册界面改造方向

- 从当前通用弹窗改为更完整的患者端账户面板或高质量弹窗。
- 精简字段与描述密度。
- 明确隐私说明和表单收益。
- 强化错误提示、焦点状态和移动端输入体验。

## 9. 视觉系统

### 9.1 设计关键词

- 医疗可信
- 冷静清晰
- 高可读性
- 面向患者
- 低噪声

### 9.2 视觉方向

- 放弃当前偏暖纸张感和编辑性文档气质。
- 改为浅冷色医疗阅读界面。
- 视觉重点是阅读、区分层级和可信赖，而不是“AI 感”。

### 9.3 色彩系统

建议采用医疗蓝青 + 健康绿的语义系统：

- 主色：冷静蓝青
- 强调色：健康绿
- 背景：浅冷白或浅蓝白
- 危险色：清晰红色
- 边框：低饱和浅青

语义要求：

- 风险信息不能只靠颜色表达。
- 成功、提醒、危险、信息都要有文本或图标辅助。

### 9.4 字体系统

推荐方向：

- 标题：`Lexend`
- 正文和 UI：`Source Sans 3`

原因：

- 高可读性
- 医疗产品感比当前衬线阅读风更稳定
- 适合标题、导航、结果说明和长段落

### 9.5 组件气质

- 中等圆角
- 低噪声阴影
- 大标题与小标签层级清晰
- 卡片分组明确
- 焦点态明显且统一

### 9.6 动效原则

- 只保留有意义的过渡：
  - 区块显现
  - 状态切换
  - 保存反馈
- 去除装饰性强、容易制造“AI 演示感”的视觉动效
- 尊重 `prefers-reduced-motion`

## 10. 组件与模块映射

### 10.1 保留并重构的核心模块

- `HomePage`
- `ConversationSidebar`
- `ConversationMessage`
- `HealthReport`
- `DiagnosisReport`
- `ChatComposer`
- `AuthModal`
- `UserMenu`

### 10.2 结构调整方向

- `ConversationSidebar` 从会话抽屉转为 `My Reports` 列表容器或桌面导航列。
- `ConversationMessage` 弱化“轮次消息”视觉，转向报告段落容器。
- `HealthReport` 与 `DiagnosisReport` 重组为统一的患者阅读型结果结构。
- `ChatComposer` 从聊天输入框转为任务导向的上传/说明输入区。
- `AuthModal` 与 `UserMenu` 的语义从工程账户功能转向患者报告保存与隐私入口。

### 10.3 数据模型策略

- 底层仍可继续复用 session/message 模型以降低重构风险。
- 视图层将 session 映射为 report item。
- 视图层将 message/result 重新映射为阅读段落和信息卡片，而不是聊天轮次。

### 10.4 路由与实现边界

- 本次前端应从“单个工作台承载全部内容”演进到“多目的地产品结构”。
- 可以先在现有应用壳中完成页面切换和视图分层，再决定是否进一步引入完整路由重构。
- 无论底层实现是条件渲染还是正式路由，用户心智上都必须看到独立目的地：
  - `My Reports`
  - `Read a Report`
  - `Upload ECG`
  - `Account`
- 不允许在视觉上继续表现为“只有一个聊天页，其他功能只是弹层或抽屉”。

## 11. 状态流与数据流

### 11.1 主流程

1. 用户进入 `Read a Report`
2. 上传报告或 ECG 资料
3. 系统提交分析请求
4. 展示结果页
5. 用户决定是否保存到 `My Reports`
6. 登录后可在 `My Reports` 中回看

### 11.2 关键状态

- 上传中
- 解析中
- 生成解释中
- 结果成功
- 结果失败
- 未登录但可阅读
- 未登录且尝试保存

### 11.3 关键映射原则

- 状态描述应使用患者可理解语言。
- 系统内部 phase 可以保留，但界面文案不能暴露工程化状态名。

## 12. 空状态、错误状态与边界处理

### 12.1 空状态

- `My Reports` 空状态应解释“这里会保存你读过的报告”。
- 首次使用时给出清晰的两个入口：
  - 读懂已有报告
  - 上传 ECG

### 12.2 错误状态

- 上传失败：说明文件格式或网络问题，并给出重试方法。
- 解析失败：说明无法识别报告内容或 ECG 数据缺失。
- 生成失败：说明系统暂时无法完成解释，并可重试。
- 所有错误提示要包含恢复路径，而不是只显示失败。

### 12.3 数据质量警告

- QC 或 pipeline warnings 继续保留。
- 表达方式改为患者可理解的提示，例如“图像质量可能影响结果准确性”。

## 13. 无障碍与响应式要求

### 13.1 无障碍

- 正文对比度至少满足 WCAG AA。
- 风险提示不能只用颜色。
- 所有图标按钮都需要可访问名称。
- 表单错误提示需要 `aria-live` 或等价能力。
- 保留清晰焦点环。

### 13.2 响应式

- 采用移动优先。
- 移动端使用底部 4 项导航。
- 桌面端使用左列 + 主阅读区。
- 避免导致浏览器返回行为混乱的手势和横向主交互。
- 结果页卡片在移动端按纵向顺序展开，避免宽表格和并列信息挤压。

## 14. 测试策略

### 14.1 组件测试

- 结果页信息排序是否固定为设计顺序
- 风险提示是否有文本表达
- 游客模式与保存登录提示是否正确触发
- `My Reports` 列表项映射是否正确

### 14.2 交互测试

- 登录/注册关键路径
- 上传到查看结果的主路径
- 从结果页保存到 `My Reports`
- 删除、重命名、导出

### 14.3 响应式测试

- 375px 移动端
- 768px 平板
- 1024px 桌面
- 1440px 宽屏

### 14.4 无障碍测试

- 键盘导航
- focus 顺序
- aria 标签
- 错误提示宣告
- reduced motion

## 15. 实现边界与阶段建议

### 阶段一

- 顶层导航重构
- 首页双入口重构
- 结果页信息结构统一

### 阶段二

- `My Reports` 替代当前会话列表
- 登录与保存流重构
- 移动端导航定型

### 阶段三

- 视觉系统收口
- 文案统一
- 响应式和无障碍补强

## 16. 最终结论

本次前端重构应将 ECG Diagnosis Suite 从“对话式分析工作台”升级为“患者阅读工作台”。

最终产品核心应是：

- 以 `读懂已有报告` 为主入口
- 以 `核心结论` 为结果页首位
- 以 `My Reports` 替代聊天历史
- 以患者医疗解释型语言组织所有结果内容
- 以可信、冷静、高可读性的医疗阅读视觉系统承载整体体验

如果后续实现过程中出现“继续保留聊天界面作为主结构”与“转向报告阅读工作台”之间的冲突，应优先选择后者。
